- **2023 바레인 GP**, **2025 헝가리 GP**, **2026 헝가리 GP** 데이터를 각각 추출하여 드라이버 간 주행 패턴(VER vs LEC / VER vs HAM / VER vs ANT) 비교 분석을 수행함.

- 코드 단에서 오프셋이나 원점(0m) 수동 보정을 시도했으나 텔레메트리 꼬임 현상이 **해결되지 않음**을 확인하고, 원본 서버 데이터 정제 상태의 중요성을 파악함.
- 로컬 성능 최적화를 위해 생성된 데이터 캐시 폴더(`f1_cache`)의 역할을 이해하고 `.gitignore`를 통해 Git 추적 대상에서 제외 처리함.

## 🛠️ FastF1 주요 메서드 및 기능 정리 ([FastF1.py](../0729/FastF1.py) 내 활용)

[FastF1.py](../0729/FastF1.py) 코드에 사용된 FastF1 핵심 메서드들의 역할 정리:

### 1. 세션 및 로딩 관련 메서드
* **`fastf1.Cache.enable_cache('f1_cache')`**
  - 지정한 로컬 디렉토리에 API 응답 데이터(`car_data`, `position_data` 등)를 파일 형태로 캐싱함.
  - 동일한 세션을 반복 조회할 때 API 호출을 줄여주고 로딩 속도를 획기적으로 개선함.
* **`fastf1.get_session(year, grand_prix, session_type)`**
  - 특정 연도, 연달(또는 서킷 이름), 세션 종류(`'Q'`: 예선, `'R'`: 본선 등)를 지정하여 세션 객체를 생성함.
* **`session.load()`**
  - F1 원본 서버 또는 로컬 캐시로부터 해당 세션 전체 데이터(랩타임, 텔레메트리, 무전, 날씨 등)를 실제로 불러옴.

### 2. 랩(Lap) 추출 관련 메서드
* **`session.laps.pick_driver('VER')`**
  - 전체 세션 데이터 중 특정 드라이버(예: Max Verstappen)의 랩 기록만 필터링함.
* **`pick_fastest()`**
  - 필터링된 랩 중 최단 시간(Fastest Lap)을 기록한 단 하나의 랩 객체를 반환함.
* **`pick_quicklaps()` / `pick_accuracy()`**
  - 피트인/아웃 랩, 세이프티카(SC) 상황, 백엔드 데이터 누락이 발생한 무효 랩을 제외하고 정상적인 주행 데이터만 정제할 때 사용하는 메서드.

### 3. 텔레메트리(Telemetry) 처리 메서드
* **`lap.get_telemetry()`**
  - 선택한 랩의 초단위(Hz 단위) 차량 센서 데이터(Speed, Throttle, Brake, RPM, Gear, Date/Time 등)를 pandas DataFrame 형태로 반환함.
* **`add_distance()`**
  - 각 센서 기록 시점의 속도와 시간 변화량을 계산하여, 랩 시작점부터의 누적 이동 거리(`Distance` 컬럼, 단위: m)를 DataFrame에 자동으로 추가해 줌.

## 🔍 핵심 이슈 및 트러블슈팅 (Troubleshooting)

### 🚨 2026 헝가리 GP 데이터 왜곡 및 수동 보정 실패 원인
- **상황**: [FastF1.py](../0729/FastF1.py)에서 2026 헝가리 GP 레이스 데이터 분석 시 드라이버 간 코너 진입 시점이 전혀 맞지 않고 속도/스로틀 그래프 파형이 심하게 엇갈림.
- **원인 및 결과**:
  1. 2026 헝가리 GP는 **실제 레이스 경기는 완전히 끝났으나, FIA/FOM 서버 측에서 센서 타임스탬프 데이터 정제(Post-Session Sync)가 아직 반영되지 않은 상태**임.
  2. 코드 상에서 `Distance` 원점(0m)을 강제로 맞추거나 오프셋 조정을 시도했으나, 데이터 원본의 타임스탬프 동기화 자체가 깨져 있어 **클라이언트 단의 수동 보정만으로는 해결이 불가능했음**.
  3. 과거 정제 완료된 데이터(2023 바레인, 2025 헝가리)와 달리, 방금 끝난 최근 세션은 백엔드 데이터가 업데이트(재정제)될 때까지 기다려야 정상 시각화가 가능함.

### 📁 캐시 폴더 버전 관리 (`.gitignore`)
- FastF1 캐싱으로 인해 수십 MB 이상의 비가공 바이너리/텍스트 파일이 생성됨.
- 저장소 용량 낭비 및 불필요한 Git tracking(`U` 상태)을 막기 위해 `.gitignore`에 `f1_cache/`를 등록하여 레포지토리 저장 대상에서 제외.

## 💡 배운 점 (Key Takeaways)
1. **데이터 파이프라인 수명주기 이해**: 방금 막 끝난 F1 세션 데이터는 원본 수신 스트림 데이터(Raw/Live Stream)와 서버 측 후처리가 완료된 정제 데이터(Post-processed) 간 차이가 존재함을 확인함.
2. **코드 보정의 한계 파악**: 데이터 소스 자체의 타임스탬프 동기화가 불량한 경우, 코드상의 단순 수학적 오프셋 보정이나 0점 맞춤으로는 한계가 있음을 직접 검증함.
